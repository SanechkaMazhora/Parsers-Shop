# Анализ источника: Красное & Белое

## 1. Источник данных

Парсер использует официальный сайт сети `Красное & Белое` и обращается напрямую к публичным JSON-эндпоинтам.

URL и эндпоинты, которые явно видны в коде:

- базовый URL по умолчанию: `https://krasnoeibeloe.ru`
- список городов: `https://krasnoeibeloe.ru/api/cities/list/`
- альтернативный вариант списка городов: `https://krasnoeibeloe.ru/api/cities/list`
- магазины по городу: `https://krasnoeibeloe.ru/api/cities/{city_id}/shops/`

Базовый URL может быть переопределен через `STORE_PARSER_KB_BASE_URL`, но по умолчанию используется официальный источник.

## 2. Формат данных

В текущей реализации используются только JSON-ответы.

Код реально поддерживает несколько вариантов структуры:

- список городов как массив объектов
- список городов как словарь с вложенным списком
- список магазинов как массив объектов
- список магазинов как словарь, где магазины лежат в ключах `shops`, `data`, `items` или `results`

HTML-страницы, встроенный JavaScript, `data-*` атрибуты и браузерный рендеринг для этого источника не используются.

## 3. Параметры запросов и доступ

- Аутентификация: в текущей реализации не используется.
- Токены доступа: в текущей реализации не используются.
- Cookies: специально не устанавливаются.
- Специальные заголовки источника: не используются.
- Общие заголовки: запросы выполняются через общий `HttpClient`, который добавляет браузерный заголовок `User-Agent`.
- Proxy-поддержка: отдельная настройка proxy в проекте не реализована.
- Обработка 18+: отдельный обход age-gate для этого источника в коде не реализован.

Все обращения к источнику выполняются методом `GET`.

## 4. Защита и ограничения источника

- Явных признаков CAPTCHA в текущей реализации не зафиксировано.
- Специальной логики обхода блокировок по IP, VPN или по `User-Agent` в коде нет.
- Для нестабильных ответов используется общий механизм повторных попыток в `HttpClient` для статусов `429`, `500`, `502`, `503`, `504`.
- Таймауты учитываются: по умолчанию используется `20` секунд, значение можно изменить через `STORE_PARSER_TIMEOUT`.
- Структура JSON может меняться в пределах нескольких близких вариантов, поэтому код уже учитывает разные формы вложенности.
- Если основной endpoint списка городов недоступен, парсер пробует альтернативный URL.

Важно: отдельной логики обхода возрастного подтверждения 18+ для `Красное & Белое` нет. Если доступ к JSON-эндпоинтам начнет зависеть от такого подтверждения, это потребует доработки кода.

## 5. Способ получения данных

Фактический алгоритм парсинга:

1. Выполнить запрос к списку городов.
2. Если первый endpoint недоступен, попробовать альтернативный вариант URL.
3. Извлечь список городов из JSON в одной из поддерживаемых структур.
4. Если в ответе есть список регионов, построить таблицу соответствий `regionId -> regionName`.
5. Для каждого города получить его числовой `id`.
6. Для каждого `city_id` выполнить запрос к `/api/cities/{city_id}/shops/`.
7. Нормализовать каждый магазин в `StoreRecord`.
8. Для `region` использовать данные магазина, города или резервное значение из `regionId`, если человекочитаемое название региона отсутствует.
9. Удалить дубликаты городов и финальных записей.

Парсер не использует браузерную автоматизацию, пагинацию, карту, фильтры интерфейса или промежуточные HTML-страницы.

## 6. Доступные поля

### Основные поля

Наиболее устойчиво в текущей реализации заполняются:

- `network`
- `city`
- `address`
- `source_url`

### Поля, заполняемые по возможности

Заполняются только если источник реально отдает эти данные:

- `region`
- `work_time`
- `latitude`
- `longitude`
- `phone`
- `store_format`
- `status`

## 7. Ограничения по данным

- `region` не всегда приходит явно в карточке магазина и иногда восстанавливается только из данных города.
- Если регион в источнике представлен только идентификатором, может быть сформировано резервное значение вида `Регион #<id>`.
- Координаты могут быть неполными: одна координата может присутствовать, а вторая отсутствовать.
- `phone`, `store_format` и `status` не гарантированы для каждой записи.
- Структура `workTime` может отличаться: строка, словарь, массив или отсутствие значения.

## 8. Стратегия устойчивости

Реально реализованные механизмы устойчивости:

- повторные HTTP-попытки через `urllib3.Retry`
- настраиваемый таймаут через `STORE_PARSER_TIMEOUT`
- настраиваемое количество повторных попыток через `STORE_PARSER_RETRIES`
- браузерный заголовок `User-Agent` для всех запросов
- попытка использовать два варианта endpoint для списка городов
- логирование warning/error без аварийного завершения всего процесса на первом локальном сбое
- пропуск отдельных городов, если запрос по конкретному `city_id` завершился ошибкой
- пропуск отдельных магазинов, если не удалось нормализовать одну запись
- дедупликация городов и магазинов
- корректная обработка пустого результата: если города не получены, парсер возвращает пустой список, а не падает исключением

Явные задержки между HTTP-запросами в коде не реализованы. Обход выполняется последовательно, без параллельного агрессивного скрейпинга.
