# Анализ источника: Монетка

## 1. Источник данных

Парсер использует официальный сайт сети `Монетка` и работает не со стабильным публичным JSON API, а с HTML-страницами сайта.

URL и шаблоны страниц, которые явно видны в коде:

- стартовая страница: `https://www.monetka.ru/shops_map/`
- страницы регионов обнаруживаются динамически по ссылкам, оканчивающимся на `/change`
- страницы городов распознаются по паттерну `https://www.monetka.ru/<region>/shops_map/<city>`
- страницы магазинов распознаются по одному из паттернов:
  - `https://www.monetka.ru/shops_map/<city>/<store_id>`
  - `https://www.monetka.ru/<region>/shops_map/<city>/<store_id>`

Базовый URL может быть переопределен через `STORE_PARSER_MONETKA_BASE_URL`, но по умолчанию используется официальный домен.

## 2. Формат данных

В текущей реализации используются:

- HTML стартовой страницы
- HTML страниц регионов
- HTML страниц городов
- HTML страниц пагинации
- HTML страниц отдельных магазинов
- встроенные структурированные фрагменты HTML и script-блоки на страницах магазинов

Что именно реально пытается извлечь код:

- ссылки на регионы
- ссылки на города
- ссылки на магазины
- текстовые поля из HTML
- координаты из `data-*` атрибутов, `meta`-тегов и script-блоков
- географию из detail-блоков, видимого текста, structured data и согласованного контекста обхода

Headless browser и Playwright для этого источника не реализованы.

## 3. Параметры запросов и доступ

- Аутентификация: в текущей реализации не используется.
- Токены доступа: в текущей реализации не используются.
- Cookies: специально не устанавливаются.
- Общие заголовки: все запросы идут через `HttpClient` с браузерным заголовком `User-Agent`.
- Специальные заголовки: для некоторых региональных URL с `/change` добавляется заголовок `Referer: https://www.monetka.ru/shops_map/`.
- Proxy-поддержка: отдельная настройка proxy в проекте не реализована.
- Обработка 18+: для `Монетки` в коде не реализована и не используется.

Запросы выполняются методом `GET`.

## 4. Защита и ограничения источника

- Явных признаков CAPTCHA в текущей реализации не зафиксировано.
- Явной логики обхода блокировок по IP, VPN или по `User-Agent` в коде нет.
- Источник может возвращать ожидаемые `404` для некоторых city/pagination страниц. Это поведение в коде обработано отдельно и логируется как `WARNING`, а не как критическая ошибка.
- Для сетевых ошибок, таймаутов и статусов `429`, `500`, `502`, `503`, `504` действует общий механизм повторных попыток в `HttpClient`.
- Динамический рендеринг карты и кластеров из исходного ТЗ в проекте не используется: текущая реализация заменяет интеракции с картой последовательным HTML-обходом страниц.
- Если стартовый этап обхода не может получить исходную страницу или список регионов, парсер поднимает модульный сбой парсера, который затем обрабатывается уровнем запуска в `main.py`.

## 5. Способ получения данных

Фактический алгоритм парсинга:

1. Загрузить стартовую страницу `/shops_map/`.
2. Из HTML извлечь ссылки на страницы регионов.
3. Для каждого региона открыть его страницу и извлечь ссылки на страницы городов.
4. Для каждого города обойти саму страницу и найденную пагинацию.
5. Со страниц города извлечь ссылки на магазины и краткий резервный контекст: адрес, режим работы и часть географии.
6. Для каждой страницы магазина загрузить страницу магазина и попытаться извлечь:
   - адрес
   - режим работы
   - формат
   - статус
   - телефон
   - город
   - регион
   - координаты
7. Если страница магазина недоступна по сетевой причине, попытаться сохранить частичную запись на основе уже собранного контекста.
8. Согласовать `city` и `region` с контекстом обхода только если он не конфликтует с более сильными сигналами страницы.
9. Удалить дубликаты финальных магазинов.

Парсер не использует автоматическое управление картой, увеличение масштаба, клик по кластерам или браузерную автоматизацию.

## 6. Доступные поля

### Основные поля

Наиболее устойчиво в текущей реализации заполняются:

- `network`
- `source_url`
- `address` — если он есть в листинге или на странице магазина
- `work_time` — если его удается получить из листинга или страницы магазина

### Поля, заполняемые по возможности

Заполняются только при наличии достаточных сигналов в источнике:

- `city`
- `region`
- `latitude`
- `longitude`
- `phone`
- `store_format`
- `status`

## 7. Ограничения по данным

- У части магазинов страницы магазинов могут быть недоступны, поэтому итоговая запись может остаться частичной.
- `city` и `region` специально не заполняются по слабым признакам, если страница не дает надежного подтверждения.
- `phone` публикуется только если найден store-specific контакт; общий телефон сайта сознательно не используется как телефон магазина.
- `store_format` и `status` доступны не для всех страниц.
- Координаты могут отсутствовать даже при наличии HTML-страницы магазина.
- Паттерны URL и структура HTML могут меняться на стороне сайта без предупреждения.

## 8. Стратегия устойчивости

Реально реализованные механизмы устойчивости:

- общий механизм повторных попыток `HttpClient` для `429` и `5xx`
- настраиваемый таймаут через `STORE_PARSER_TIMEOUT`
- настраиваемое количество повторных попыток через `STORE_PARSER_RETRIES`
- браузерный заголовок `User-Agent`
- специальный `Referer` для части региональных `/change`-страниц
- последовательный обход без параллельного агрессивного скрейпинга
- ограничение на пагинацию: не более `20` страниц на один городской обход
- отдельная обработка ожидаемых `404` на уровне city/pagination
- сохранение частичной записи, если страница магазина недоступна, но базовые данные уже собраны
- логирование ошибок запросов с разделением на стартовые сбои и локальные сценарии, после которых работа может продолжаться
- дедупликация итоговых записей

Явные задержки между HTTP-запросами в коде не реализованы. Вместо этого проект опирается на повторные попытки, последовательный обход и аккуратную обработку ошибок.
