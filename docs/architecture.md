# Architecture

## Overview

Проект выполняет live end-to-end сбор магазинов из официальных источников, нормализует данные в единую схему и сохраняет результат в Excel плюс snapshot JSON для diff между полными запусками.

Базовый pipeline:

1. `main.py` выбирает нужные parser-модули.
2. Каждый parser получает live-данные из своего источника и возвращает `list[StoreRecord]`.
3. Общий export-слой нормализует output, пишет `stores.xlsx`, сохраняет snapshot baseline и считает diff.
4. Orchestration завершает процесс с exit code, который отражает итог run для cron / Task Scheduler.

## Parser Contract

Каждый parser отвечает за:

- получение данных из источника
- преобразование их в канонический `StoreRecord`
- локальную обработку ожидаемых проблем источника, если возможно сохранить частичный или полный результат

Разделение ответственности:

- recoverable warning — parser сам обработал проблему источника, залогировал ее и все равно вернул результат из `parse()`
- parser-level failure — `parse()` завершился необработанным исключением и parser считается упавшим как модуль

Если один parser падает как модуль, orchestration продолжает остальные parser-ы, экспортирует доступные данные и завершает run с non-zero exit code.

## Run Semantics

С точки зрения orchestration:

- exit code `0` возвращается только если все выбранные parser-ы завершились без необработанного исключения
- exit code `1` возвращается если хотя бы один выбранный parser завершился parser-level failure
- exit code `130` возвращается при ручном прерывании run

Важно:

- warning в логах не означает failed run сам по себе
- успешный run может содержать частично заполненные записи, если parser надежно сохранил то, что источник действительно отдал
- partial Excel / snapshot могут быть записаны и при exit code `1`, но это неполный run

## Data Model

Каноническая output schema `StoreRecord`:

- `network`
- `region`
- `city`
- `address`
- `work_time`
- `latitude`
- `longitude`
- `phone`
- `store_format`
- `status`
- `source_url`
- `collected_at`

Эта схема используется:

- в Excel-листе `Актуальные данные`
- в snapshot JSON
- в payload листа `Изменения`

Принципы нормализации:

- схема стабильна для всех сетей
- отдельные поля некоторых сетей являются best-effort
- если значение нельзя восстановить надежно, проект сохраняет `None` / `null`
- противоречивые или технические сигналы не должны публиковаться как факт

Legacy-алиасы `lat`, `lng`, `parsed_at` поддерживаются как совместимый вход, но не считаются каноническим output.

## Snapshot And Diff

Diff сравнивает два полных snapshot-среза.

Определения:

- `added` — запись есть в новом snapshot, но не было в предыдущем baseline
- `removed` — запись была в предыдущем baseline, но отсутствует в новом snapshot
- `changed` — запись совпала по `stable_key`, но изменились отслеживаемые бизнес-поля

Свойства механизма:

- baseline хранится в отдельном snapshot JSON
- первый полный запуск только инициализирует baseline и не заполняет diff шумом
- `stable_key` строится детерминированно и используется для воспроизводимого сопоставления магазинов между запусками
- `collected_at` не используется как причина для `changed`
- snapshot и финальный Excel канонизируются по `stable_key`, чтобы одна store identity не сохранялась дублями

## Logging

Логирование отражает серьезность события, а не просто факт проблемы.

- обработанные source-level проблемы логируются как `WARNING` или ниже, если run продолжается штатно
- parser-level failure и непредвиденные сбои логируются как `ERROR`
- expected Monetka `404`, если parser их обработал и продолжил run, не должны создавать впечатление аварийного полного запуска

## Network-Specific Reliability

- Monetka: geography публикуется только из надежных сигналов; при конфликте между страницами parser предпочитает `None`, а не ложный `city` / `region`
- Maria-Ra: `region` часто недоступен надежно и остается `None`, если источник не дает явного основания
- В любой сети отсутствующие значения сохраняются как `null`, если восстановление было бы спекулятивным
